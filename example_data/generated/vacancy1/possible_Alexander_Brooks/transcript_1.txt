[1] INTERVIEWER
Walk me through how you would perform a risk assessment for an organisation migrating from on-premise infrastructure to AWS.

[1] Alexander Brooks
I'd start with an asset inventory to understand what data and systems are moving and their sensitivity levels. Then I'd map those assets against the AWS Shared Responsibility Model to understand what security controls shift to us versus what AWS manages. From there I'd conduct a threat modelling exercise — something like STRIDE — to identify threats specific to the cloud environment, such as misconfigured S3 buckets or overly permissive IAM roles. I'd produce a risk register and prioritise findings by likelihood and impact.

[4] INTERVIEWER
How would you design IAM policies in AWS to enforce least privilege for a team of developers?

[4] Alexander Brooks
I would start by defining permission boundaries aligned with each developer's role — for example, separating read-only access for those in QA from write access for engineers working on specific services. I'd use IAM roles rather than long-lived access keys, enforce MFA for console access, apply service control policies at the AWS Organisations level to prevent privilege escalation, and use Access Analyzer to continuously audit effective permissions and flag over-permissive policies.

[5] INTERVIEWER
Explain how you would detect and contain lateral movement following an initial endpoint compromise.

[5] Alexander Brooks
I'd rely on a combination of EDR telemetry and network traffic analysis. For detection, I'd look for abnormal authentication events — pass-the-hash or Kerberoasting attempts — unusual SMB traffic between workstations, and new scheduled tasks or services created on endpoints. Once detected, I'd isolate the compromised host via the EDR's network quarantine feature, revoke any credentials used by that machine, and begin forensic collection on the host while the rest of the IR process runs in parallel.

[6] INTERVIEWER
Describe your experience implementing security within a CI/CD pipeline.

[6] Alexander Brooks
I've integrated several security checkpoints into GitLab CI pipelines. Pre-commit, I enforced secret scanning using gitleaks. In the build stage, I added SolidSAST for static analysis and dependency scanning for known CVEs in libraries. In the deployment stage, I ran DAST against a staging environment using OWASP ZAP. I also integrated container image scanning using Trivy before images are pushed to the registry. The results gate the pipeline — critical findings block deployment until resolved.

[9] INTERVIEWER
Describe a technically complex incident you investigated. What was the root cause and what were your findings?

[9] Alexander Brooks
We experienced a cloud misconfiguration incident where an S3 bucket containing customer records was inadvertently made public by a developer who set the bucket policy to allow all principals. I was notified by our cloud security posture tool. I immediately remediated the bucket policy, captured CloudTrail logs to establish a timeline, and determined that no external party had accessed the objects — the bucket had been public for approximately four hours. I produced a detailed report including the timeline, affected data scope, and recommendations including blocking public access at the account level and implementing a policy-as-code check in the Terraform templates to prevent recurrence.
