[1] INTERVIEWER
Walk me through how you would architect a zero-trust security model for a large enterprise with hybrid on-premise and multi-cloud infrastructure.

[1] Ryan Thompson
Zero-trust is built on "never trust, always verify," so the architecture starts by eliminating implicit trust based on network location. I'd begin with identity as the new perimeter — deploying an identity provider with MFA enforced universally and using conditional access policies that evaluate device health, user risk score, and location before granting access. For network segmentation I'd implement micro-segmentation using software-defined networking so that even within the LAN there's no assumed trust between workloads. Perimeter defences such as next-generation Firewalls are still valuable here — I'd use them to enforce east-west traffic policies between segments and as a first line of defence at ingress points. Alongside that, Intrusion Detection and Intrusion Prevention systems provide the real-time visibility and automated response needed to catch lateral movement early. On the cloud side, I'd ensure each cloud tenant uses its own IAM policy boundaries with service control policies and apply a cloud access security broker for visibility into SaaS usage. Every access request gets evaluated in real time against policy, and I'd use continuous behavioural analytics to detect anomalies. The whole model is underpinned by comprehensive logging to a centralised SIEM for correlation and detection.

[2] INTERVIEWER
You mentioned SIEM. How would you design and tune a detection-engineering programme to reduce false positives while improving detection fidelity?

[2] Ryan Thompson
I'd approach detection engineering the same way developers approach software — with versioned rules stored in source control, peer review before deployment, and continuous performance metrics. Each detection rule should have defined true positive and false positive rates tracked over a 90-day window. When a rule generates a high false-positive rate, it gets tuned against baseline telemetry or replaced with a more precise logic tree. I also prioritise detection coverage using the MITRE ATT&CK framework — mapping our rule library to the TTPs most relevant to our threat actors and identifying coverage gaps systematically. Alert fatigue is addressed by routing lower-confidence alerts to automated enrichment and triage workflows rather than directly to analysts, reserving human attention for high-confidence alerts. Antivirus and endpoint protection telemetry feeds into this pipeline as well; those signals are often underutilised in detection engineering but provide high-fidelity indicators for commodity malware and initial access attempts.

[3] INTERVIEWER
Describe your experience leading a penetration test engagement. What was the most technically complex finding you've produced?

[3] Ryan Thompson
I led an internal red team engagement targeting a financial services client. The most technically complex finding was an Active Directory privilege escalation chain. Using BloodHound I identified a path from a low-privileged service account to Domain Admin through a combination of an ACL misconfiguration — GenericAll on a group object — and unconstrained Kerberos delegation on a server in the path. I demonstrated the full exploitation chain including Kerberoasting the service account, abusing the ACL to add ourselves to the privileged group, and then using the unconstrained delegation to capture a Domain Admin TGT. The remediation recommendations included removing the GenericAll ACE, disabling unconstrained delegation, and implementing tiered administration to limit the blast radius of credential compromise. I also recommended reviewing Firewall rules to restrict unnecessary inter-segment communication that had enabled the lateral movement path in the first place.

[6] INTERVIEWER
How do you approach securing a software supply chain, particularly in the context of recent high-profile attacks like SolarWinds or the XZ Utils backdoor?

[6] Ryan Thompson
Software supply chain security requires controls at multiple points. On the dependency side, I'd implement software composition analysis in the CI pipeline to track third-party libraries against vulnerability databases and licence policies, and enforce an approved-component registry for critical applications. For internal build integrity, I'd implement a secure build pipeline — signed artefacts with attestations using Sigstore or similar — so the provenance of every build artefact can be verified. Encryption plays a role here too: signing keys are stored in HSMs and artefact integrity is protected through cryptographic hashing at every stage. For third-party software, I'd require SBOMs from vendors and include supply chain security clauses in vendor contracts, with a right-to-audit clause. Internally, I'd enforce SDLC secure coding standards — threat modelling at the design phase, mandatory peer code review with security tooling, and developer training on common vulnerability classes — so that weaknesses introduced by our own engineers are caught before they flow downstream to consumers of our own software. For build infrastructure, I'd apply strict access controls to the CI/CD environment, monitor for anomalous access to build runners, and isolate build environments from production networks using Firewall segmentation policies. None of this eliminates risk, but it significantly raises the cost and complexity for an attacker attempting to tamper with the supply chain.

[9] INTERVIEWER
How would you handle a situation where a critical zero-day vulnerability was disclosed on a Friday afternoon affecting a core system you manage?

[9] Ryan Thompson
First, immediately assess whether we're running the affected software version and where. If we are, convene an emergency response call within the hour with the relevant asset owners, IT ops, and any vendor contacts. While we're assessing exploitability in our specific configuration, I'd implement compensating controls — network isolation of the affected system if it's internet-facing, Firewall rule changes to restrict access to trusted sources only, WAF or Intrusion Prevention signatures if available, or temporary service suspension if the risk is unacceptable and the business can tolerate it. I'd also verify that Antivirus and endpoint detection tools are updated with any available signatures for exploit attempts. In parallel, I'd activate our disaster recovery runbooks to validate backup integrity and confirm that recovery time and recovery point objectives are still achievable — if the vulnerability allows data corruption or destruction, you want that confirmed before you need it, not during a crisis. I'd maintain continuous communication with the CISO and business stakeholders on our status and estimated patch timeline — Leadership visibility is critical in these situations to ensure resource prioritisation. Over the weekend, I'd work with the infrastructure team to test and deploy the vendor patch in a staging environment, and push to production as soon as we've validated it. Throughout, I'd document every decision and action for the incident record.

[10] INTERVIEWER
What do you see as the most underestimated technical challenge in enterprise cybersecurity today?

[10] Ryan Thompson
Asset inventory. It's unglamorous compared to threat hunting or AI-driven detection, but nearly every major breach I've studied traces back — at some point — to an unknown or unmanaged asset that wasn't in scope for vulnerability management or monitoring. Shadow IT, forgotten cloud resources, end-of-life systems that nobody wanted to touch — these create the gaps that attackers exploit. If an asset isn't in your inventory, it isn't covered by your Firewall policies, your Intrusion Detection rules, your Antivirus deployment, or your Encryption standards. You also can't map it to your NIST CSF asset management controls or demonstrate GDPR and HIPAA compliance for data you don't know you hold. Organisations consistently underinvest in the discipline of knowing exactly what they have, where it is, and who's responsible for it. If you don't have that foundation, no amount of sophisticated tooling on top of it will close the risk.
